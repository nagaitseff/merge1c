# Разработка и проверки

## Подготовить окружение

```powershell
python -m pip install -e .
python -m unittest discover -s tests -v
```

Тесты используют стандартный unittest. Для интеграционных проверок Git должен быть в PATH. Они создают собственные временные репозитории и не работают с ERP разработчика.

Для статической проверки доступен отдельный набор зависимостей разработки:

```powershell
python -m pip install -e ".[dev]"
ruff check src tests examples
```

Используется Ruff 0.17.2 с явным набором правил в `pyproject.toml`: ошибки импортов и имён, подозрительные конструкции и проверки Bugbear. Для работы самой библиотеки Ruff не нужен. Автоматический форматтер не запускается над пользовательской выгрузкой.

На Windows полный прогон также запускает доступные PowerShell 5.1, PowerShell 7 и cmd. Эти проверки специально используют кириллицу, пробелы, символ `&`, старую кодовую страницу и внешнюю программу. Отдельно проверяется `--quiet` при строгой обработке ошибок PowerShell 5.1.

## Перед завершением изменения

Проверьте следующие вопросы:

1. Понятно ли пользователю, какую команду выполнить и где найти результат?
2. Можно ли прервать работу и продолжить без повторного решения уже разобранных случаев?
3. Сохранились ли исходники и оформление нетронутых участков?
4. Не появилась ли незаметная потеря правки, дублирование или произвольное сопоставление объектов?
5. Измерены ли время и память, если изменился алгоритм обхода или хранения?
6. Совпадают ли примеры документации с фактическим API и кодами завершения?
7. Проверяются ли ошибки, частично поддержанные случаи и отмена внешнего инструмента?

## Как добавлять поддержку

Для нового вида XML сначала добавьте независимые примеры: базу, две стороны и ожидаемый результат. Укажите области ID, значимый порядок и ссылки. Добавьте как успешные, так и неоднозначные случаи. Непонятная структура не должна становиться успешной только потому, что её удалось разобрать как XML.

Для BSL отделяйте лексический индекс от платформенной проверки. Расширение препроцессорной поддержки требует испытаний на разных контекстах исполнения, а не только поиска ключевых слов.

При работе с Git проверяйте реальные временные репозитории: ancestry результата, неизменность index и рабочей копии, устаревший HEAD, активную операцию, повторное имя ветки и GC входов сессии.

## Измерить производительность

```powershell
python examples/benchmark.py --records 1000
python examples/benchmark.py --records 5000
```

Обычное время и запуск с tracemalloc измеряются отдельно: трассировка сама замедляет выполнение. Отчёт содержит размер документа и число изменений. Это синтетическая нагрузка, а не прогноз времени обновления ERP.

## Документация

Описание команды и пример использования обновляются в том же изменении, что и код. Новая настройка должна иметь значение по умолчанию, проверку ошибок и описание влияния на сессию. Пользовательский текст пишется простыми предложениями: действие, причина, следующий шаг.
