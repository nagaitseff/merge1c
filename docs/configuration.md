# Настройки проекта и внешних программ

Настройки читаются из TOML 1.0 стандартным модулем Python `tomllib`. Требуется Python 3.11 или новее. Неизвестные ключи и неверные типы значений отклоняются: опечатка в имени настройки не должна незаметно менять правила объединения.

## Два файла настроек

`merge1c.toml` содержит правила проекта. Его можно хранить в Git: состав исходников, версию платформы, профили, аргументы внешних проверок и условия готовности кандидата.

`merge1c.local.toml` содержит пути программ на конкретном компьютере. Его следует исключить из Git. В нём разрешены только:

```toml
[git]
executable = 'C:\Program Files\Git\cmd\git.exe'

[tools.beyond_compare]
executable = 'C:\Program Files\Beyond Compare 5\BCompare.exe'
```

Каждый инструмент локального файла должен быть заранее объявлен в проекте. Локально нельзя добавить новый инструмент или изменить его `adapter`, `kind`, `args`, `timeout`, обязательность отчёта и правила проверок.

В TOML одинарные кавычки удобны для путей Windows: обратная косая черта внутри них записывается буквально. В строках с двойными кавычками её нужно удваивать: `"C:\\Tools\\python.exe"`. Для аргументов также подходят прямые косые черты: `"{project}/scripts/check_sources.py"`.

Для команды с `--repo` CLI ищет `merge1c.toml` в корне указанного репозитория. В остальных случаях — в текущем каталоге. Рядом с ним читается необязательный `merge1c.local.toml`. Другие пути задаются после команды:

```powershell
python -m merge1c config --config 'C:\ERP\merge1c.toml' --local-config 'C:\Settings\erp.local.toml' --profile vendor_update
```

Явно указанный отсутствующий файл считается ошибкой. Без проектного файла действуют встроенные значения. Команда `init` создаёт проектный файл и `merge1c.local.example.toml`; существующие файлы она не перезаписывает.

Команда `doctor` проверяет наличие Git и требуемых программ, не запуская графические инструменты и платформу. Код 2 означает ошибку окружения или отсутствие обязательного инструмента, в том числе платформенного адаптера при `require_platform = true`.

## Порядок применения

Сначала загружаются общие настройки проекта, затем выбранный профиль, затем разрешённые локальные пути. Вложенные таблицы объединяются по ключам. Массивы **заменяются целиком**, а не дополняются.

Есть два встроенных имени профиля:

| Профиль | `incoming_role` по умолчанию | Назначение |
| --- | --- | --- |
| `vendor_update` | `vendor` | Перенос своих изменений на новую поставку |
| `develop_sync` | `master` | Обновление рабочей ветки относительно основной |

Профиль выбирается через `--profile` или аргумент `profile` функции `load_config`. Дополнительный профиль должен быть объявлен в `[profiles.<имя>]`. Внутри профиля допустимы те же таблицы правил и дополнительный ключ `incoming_role` со значением `vendor`, `master` или `incoming`. Профиль не может менять `schema_version` или объявлять вложенные `profiles`.

`incoming_role` обозначает роль входящей стороны в отчёте. Он не выбирает другую стратегию слияния и не делает входящую сторону безусловным победителем конфликта.

## Схема версии 1

На верхнем уровне разрешены только `schema_version` и таблицы `project`, `git`, `xml`, `bsl`, `resolution`, `validation`, `tools`, `profiles`.

| Таблица и ключ | Значение по умолчанию | Что означает |
| --- | --- | --- |
| `schema_version` | `1` | Единственная поддерживаемая версия схемы |
| `project.source_roots` | `[]` | Относительные каталоги, в которых применяется объединение XML/BSL и их проверка |
| `project.platform_version` | `"8.3.27.2342"` | Точная ожидаемая версия в отчёте платформенного адаптера |
| `git.executable` | `"git"` | Программа Git, найденная по пути или через `PATH` |
| `git.minimum_version` | `"2.50.0"` | Минимальная версия Git для операций с репозиторием; понизить ниже 2.50 нельзя |
| `git.rename_detection` | `"domain"` | Единственное допустимое значение: сопоставление метаданных по предметным признакам |
| `xml.forms.preserve_source` | `true` | Сохранение исходного текста вне необходимых правок |
| `xml.forms.placement` | `"after_incoming_in_same_gap"` | Свои добавления идут после входящих добавлений в том же промежутке |
| `xml.forms.id_policy` | `"preserve_and_remap_collisions"` | Сохранение свободных ID; переназначение поддержанных коллизий с обновлением известных ссылок |
| `bsl.mode` | `"conservative"` | Осторожное объединение по границам методов |
| `bsl.preserve_source` | `true` | Перенос исходных фрагментов без форматирования всего модуля |
| `resolution.ambiguous` | `"manual"` | Неоднозначные случаи требуют решения |
| `resolution.manual_tool` | `""` | Имя инструмента разрешения конфликтов по умолчанию |
| `validation.required_tools` | `[]` | Имена обязательных внешних валидаторов |
| `validation.require_platform` | `true` | Для готовности требуется принятый отчёт платформенного адаптера |

Настройки сохранения текста, размещения, ID, режима BSL, предметного сопоставления и ручного разрешения сейчас задают фиксированные правила. Указанные значения допустимы; альтернативные значения отклоняются.

Пустой `source_roots` или `source_roots = ["."]` означает всё дерево. Например, `["src/cf", "src/extensions"]` ограничивает область специального разбора. Абсолютные пути, `..`, маски `*`/`?` и пути с буквой диска здесь запрещены. Повторяющиеся корни убираются, разделители нормализуются в `/`.

Это **не фильтр копирования**: кандидат содержит всё дерево. Для остальных файлов сохраняется обычный выбор неизменённой или односторонне изменённой версии. Разные одновременные изменения вне выбранных корней требуют решения.

## Описание инструмента

Каждая таблица `[tools.<имя>]` допускает следующие ключи:

| Ключ | По умолчанию | Допустимые значения и смысл |
| --- | --- | --- |
| `adapter` | `"command"` | `command`, `beyond_compare`, `platform` |
| `executable` | `""` | Путь исполняемого файла или имя из `PATH` |
| `args` | `[]` | Массив строк: один элемент — один аргумент процесса |
| `timeout` | `300` | Положительное целое число секунд |
| `kind` | `"validator"` | `validator` или `resolver`; у `beyond_compare` по умолчанию `resolver` |
| `report_required` | `false` | Обязательность JSON-отчёта; у `platform` по умолчанию `true` |

`resolution.manual_tool` должен ссылаться на инструмент с `kind = "resolver"`. Все имена из `validation.required_tools` должны ссылаться на инструменты с `kind = "validator"`. Для платформенной проверки используйте `adapter = "platform"`, `kind = "validator"`, `report_required = true`.

`platform` — контракт запуска вашей проверяющей программы. Встроенной команды загрузки конфигурации, настроенной информационной базы или автоматического распознавания результата Конфигуратора этот адаптер не предоставляет. Обёртка должна действительно выполнить нужные проверки и создать отчёт. Один удачный код возврата `1cv8.exe` нельзя автоматически считать проверкой всех модулей и поведения конфигурации.

### Аргументы и подстановки

Запуск выполняется с `shell=False`. Кавычки вокруг пути с пробелами внутри элемента массива не нужны. Конвейеры, перенаправления, `%VARIABLE%`, `$VARIABLE` и `~` автоматически не разворачиваются. `executable` не обрабатывается как шаблон; для него укажите полный путь или имя программы из `PATH`.

В Windows прямой `executable` с расширением `.bat` или `.cmd` отклоняется: такие файлы могут неявно запускаться через командный интерпретатор даже при `shell=False`. Для обёртки укажите `python.exe` и отдельный аргумент-путь к `.py` либо `powershell.exe`, `-File` и путь к `.ps1`. См. [особенности оболочек Windows](windows.md).

В `args` разрешены только простые подстановки:

| Подстановка | При разрешении файла | При проверке сессии |
| --- | --- | --- |
| `{base}`, `{local}`, `{incoming}` | Отдельные копии трёх версий файла | Каталоги сохранённых входов сессии |
| `{result}` | Новый путь, куда resolver должен записать файл | Служебный неиспользуемый путь; валидатору писать сюда не требуется |
| `{candidate}` | Каталог кандидата | Каталог кандидата |
| `{report}` | Новый путь JSON-отчёта запуска | Новый путь JSON-отчёта запуска |
| `{path}` | Относительный путь конфликтующего файла | Пустая строка |
| `{project}` | Каталог проектного TOML | Каталог проектного TOML |

Если `load_config()` вызван без пути, `{project}` соответствует текущему каталогу на момент загрузки. Отдельный локальный TOML не меняет этот корень. Путь к каталогу исходников также не переопределяет `{project}`.

Подстановки можно включать в строку, например `"--output={report}"`. Форматные спецификации, преобразования `!r`, обращения к атрибутам и индексам запрещены. Буквальные фигурные скобки в аргументе записываются как `{{` и `}}`.

Рабочий каталог процесса — новый каталог конкретного запуска внутри сессии. Для скрипта или конфигурационного файла проекта используйте `{project}`, а не относительный путь, рассчитанный на текущий каталог терминала.

### Полный пример проектного файла

В этом примере `scripts/check_sources.py` и `scripts/check_platform.py` — **ваши программы-обёртки**, а не поставляемые компоненты. До их настройки обязательные проверки не смогут завершиться успешно.

```toml
schema_version = 1

[project]
source_roots = ["src/cf"]
platform_version = "8.3.27.2342"

[git]
minimum_version = "2.50.0"
rename_detection = "domain"

[xml.forms]
preserve_source = true
placement = "after_incoming_in_same_gap"
id_policy = "preserve_and_remap_collisions"

[bsl]
mode = "conservative"
preserve_source = true

[resolution]
ambiguous = "manual"
manual_tool = "beyond_compare"

[validation]
required_tools = ["source_check"]
require_platform = true

[tools.beyond_compare]
adapter = "beyond_compare"
kind = "resolver"
timeout = 7200

[tools.source_check]
adapter = "command"
kind = "validator"
args = ["{project}/scripts/check_sources.py", "--candidate", "{candidate}", "--report", "{report}"]
timeout = 600
report_required = true

[tools.platform_check]
adapter = "platform"
kind = "validator"
args = ["{project}/scripts/check_platform.py", "--candidate", "{candidate}", "--report", "{report}"]
timeout = 3600
report_required = true

[profiles.vendor_update]
incoming_role = "vendor"

[profiles.develop_sync]
incoming_role = "master"

# Этот профиль заменяет, а не расширяет общий массив required_tools.
[profiles.static_review]
incoming_role = "incoming"

[profiles.static_review.validation]
required_tools = ["source_check"]
require_platform = false
```

Соответствующий локальный файл:

```toml
[git]
executable = 'C:\Program Files\Git\cmd\git.exe'

[tools.beyond_compare]
executable = 'C:\Program Files\Beyond Compare 5\BCompare.exe'

[tools.source_check]
executable = 'C:\Python311\python.exe'

[tools.platform_check]
executable = 'C:\Python311\python.exe'
```

`beyond_compare` с пустым `args` использует порядок `local`, `incoming`, `base`, `result` и ключи `/solo /ro` в Windows (`-solo -ro` в других ОС). Если задать непустой `args`, применяется именно ваш массив. Resolver обязан дождаться завершения работы пользователя и создать `{result}`. Реальный Beyond Compare и платформа 1С требуют проверки на вашем компьютере; эти примеры не подтверждают их совместимость с конкретной установкой.

### Отчёт внешней проверки

Файл `{report}` должен быть новым JSON-объектом в UTF-8. Минимальный успешный отчёт обычного валидатора:

```json
{"status": "passed"}
```

Платформенный адаптер дополнительно возвращает точную версию реально использованной платформы:

```json
{
  "status": "passed",
  "platform_version": "8.3.27.2342",
  "checks": ["configuration_load", "module_check"]
}
```

Поле `checks` здесь — пример дополнительных сведений: merge1c его сохраняет, но не интерпретирует и не проверяет полноту перечисленных действий. За правдивость отчёта отвечает адаптер. Версия сравнивается с `project.platform_version` как точная строка.

Успех требует кода возврата 0. Если отчёт создан, его `status` должен быть именно строкой `"passed"`; неверный JSON, JSON-массив, другой статус или отсутствие обязательного отчёта дают ошибку. Ненулевой код нельзя отменить успешным отчётом. Тайм-аут отмечается как `timeout`. Последние 64 КиБ stdout и stderr сохраняются в результате инструмента; полный журнал при необходимости пишет сама обёртка.

Проверки запускаются командой `check <сессия> --run-tools`. Выполняются обязательные валидаторы, а при `require_platform = true` — также настроенные адаптеры `platform`. Валидатор должен читать кандидат, не изменяя его. Изменение кандидата во время проверки отклоняет результат; изменение входных снимков делает сессию непригодной для продолжения.

## Снимок настроек и актуальность проверок

При создании сессии сохраняются итоговые настройки и их SHA-256. Дальнейшая правка TOML не меняет уже созданную сессию: для новых правил создайте новую. `config` показывает итоговые значения и контрольную сумму до начала работы.

Успешные результаты внешних проверок привязаны к содержимому кандидата и идентичности программы. Хешируется исполняемый файл, а также существующие файлы, на которые **целиком** указывают постоянные аргументы, включая путь вида `{project}/scripts/check_sources.py`. Если программа или такой скрипт изменились, отчёт становится устаревшим; требуется повторный `check --run-tools`. Они также проверяются до и после запуска.

Это не полная фиксация окружения: автоматически не хешируются все импорты Python, установленные библиотеки, внешние службы, переменные окружения и файлы, скрытые внутри аргумента вида `--config=путь`. Аргументы со ссылками на входы, кандидат, результат или отчёт исключены из этого индекса файлов. Для важных обёрток используйте отдельный аргумент-путь и сохраняйте сведения о зависимостях в собственном отчёте.

## Что означает отключение платформенной проверки

`validation.require_platform = false` разрешает состояние `ready` после встроенных структурных и обязательных внешних проверок без подтверждения платформой. Для Git-сессии это также разрешает создать ветку такого кандидата. Используйте это только как осознанный режим статического разбора и ревью.

В отчёте при этом остаётся `platform = "not_run"`, если актуальная платформенная проверка не принята. Это не равнозначно `platform = "passed"`, успешной загрузке конфигурации или её работоспособности. При стандартном `require_platform = true` отсутствие принятого результата точной версии платформы оставляет сессию в состоянии `prepared`.
