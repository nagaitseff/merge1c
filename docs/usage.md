# Порядок работы

## Что сравнивается

Для каталогов нужно три полных согласованных снимка:

- `base` — общее исходное состояние;
- `local` — наше состояние с доработками;
- `incoming` — новая версия, на которой строится результат.

```powershell
merge1c merge C:/sources/base C:/sources/local C:/sources/incoming --session C:/merge-sessions/manual-update
```

Исходные каталоги не меняются. Сессия не может находиться внутри входного каталога или содержать его. Уже существующая сессия не перезаписывается.

Для Git команда `prepare` берёт снимки коммитов. Текущие файлы рабочего дерева, включая незавершённые ручные решения другого merge, не подмешиваются. Программа сохраняет замечание об отличающемся рабочем состоянии. При создании ветки-кандидата активные merge/rebase/cherry-pick должны быть завершены.

Если Git находит несколько лучших общих оснований или история несвязанная, первая версия откажется от автоматической подготовки. Произвольно выбирать одно основание она не будет.

## Что означают состояния

| Состояние | Значение |
|---|---|
| `conflicts` | Остались неоднозначности или ошибки структуры |
| `prepared` | Кандидат подготовлен, но обязательные проверки ещё не завершены |
| `ready` | Пройдены проверки, требуемые сохранёнными настройками |

Отдельно указываются состояние платформенной проверки и внешних инструментов. `ready` при сознательно отключённом требовании платформы не означает `platform: passed`.

`status` повторяет структурную проверку. `check --run-tools` дополнительно запускает обязательные внешние программы. Изменение кандидата сбрасывает результаты внешних проверок. Изменившийся проверяющий executable или распознанный входной скрипт тоже требует повторного запуска.

## Как принимаются решения

Откройте `report.json` или используйте `status --json`. У каждого замечания есть код, путь и пояснение. Код удобен для поиска и автоматизации; пояснение описывает, что требует решения.

`resolve --take local` принимает нашу сторону. `--take incoming` — входящую. Для Git-профиля `develop_sync` входящая сторона — master; для `vendor_update` — поставщик. Слово `incoming` не означает одну и ту же ветку для всех операций.

`resolve --tool NAME` запускает настроенную программу с отдельными копиями сторон. Изменённый файл принимается только из выделенного выходного каталога. Если программа изменила входные копии, завершилась ошибкой или не создала результат, решение не принимается.

Можно отредактировать `candidate/` своим редактором и выполнить `resolve SESSION PATH --accept`. Это явное подтверждение конкретного нерешённого файлового случая. Структурная ошибка не исчезнет только от подтверждения: текущий результат будет проверен заново.

До запуска инструмента сохраняется предыдущий файл кандидата. История решений и рабочие копии находятся в `resolutions/`. Восстановление файла из этой истории выполняйте в кандидате, затем снова запустите проверку.

## Журнал

```powershell
merge1c events C:/merge-sessions/manual-update --tail 30
```

В журнале указаны реальные действия: начало и завершение проверок, принятие решения, создание ветки. Для автоматического сбора прогресса используйте `--json-progress`; строки JSON идут в stderr, итоговый `--json` отчёт — в stdout.

`--quiet` у `merge` и `prepare` убирает вывод прогресса в терминал, сохраняя журнал и итоговый отчёт. Для старого PowerShell учитывайте [особенности перенаправления stderr](windows.md).

## Возобновление после остановки

Если первоначальная команда `prepare` или `merge` завершилась и сохранила `session.json`, повторно создавать сессию не нужно:

```powershell
merge1c status C:/merge-sessions/manual-update
merge1c check C:/merge-sessions/manual-update
```

Настройки берутся из сохранённого снимка. Правка первоначального TOML не меняет уже начатую сессию. Для новых правил создайте новую сессию.

Команды изменения состояния защищены блокировкой. После аварийного завершения может остаться `session.lock`. Сначала убедитесь, что прежний процесс завершён, затем:

```powershell
merge1c unlock C:/merge-sessions/manual-update --force
merge1c check C:/merge-sessions/manual-update
```

Если сохранённые входы изменились, библиотека не продолжит их использовать как прежние. Создайте новую сессию из правильных исходников.

Если остановка произошла во время самой первой подготовки, каталог может ещё не содержать `session.json`. Такая незавершённая подготовка пока не возобновляется. Сохраните её отдельно, если там нужны файлы, и повторите команду с новым каталогом сессии. Первоначальные исходники не менялись. Наличие одного `candidate/` без манифеста не означает готового результата.

## Что появляется в Git

При `prepare` создаётся собственная ссылка `refs/merge1c/sessions/...`. Она удерживает входные коммиты от удаления сборщиком мусора Git. Рабочие файлы и index при этом не меняются. Текущий кандидат, решения и журнал хранятся в каталоге сессии; служебная ссылка не заменяет его резервную копию.

При `branch` создаётся merge-коммит на новой ветке. Он имеет родителей исходного HEAD и входящего коммита. Существующие ветки не двигаются и checkout не выполняется.

После завершения работы служебную ссылку можно освободить:

```powershell
merge1c release-pin C:/merge-sessions/update-2.5.27.101
```

Освобождение не удаляет каталог сессии или созданную ветку. Для ещё нужной сессии оставьте закрепление входов.

Сессия из трёх каталогов не имеет служебной ссылки Git; команда `release-pin` для неё не требуется.

## Предварительное слияние штатным Git

```powershell
merge1c git-preview vendor/2.5.27.101 --repo C:/REP/erp
```

Эта отдельная команда вызывает `merge-tree` без rename-эвристики и выводит структурированную диагностику. Она создаёт объекты Git, но не меняет index и рабочие файлы. Обычная `prepare` использует снимки и предметный Python-движок; результат `git-preview` не подставляется в XML автоматически. Установленные пользовательские merge drivers могут участвовать в штатном предварительном слиянии Git.

## Коды завершения

| Команда | 0 | 1 | 2 |
|---|---|---|---|
| `merge`, `prepare`, `resolve` | Кандидат подготовлен без нерешённых случаев | Есть нерешённые случаи | Ошибка запуска или входов |
| `check` | Кандидат готов по выбранной политике | Есть нерешённые случаи | Обязательные проверки ещё не выполнены или ошибка |
| `inspect` | Нет блокирующих структурных замечаний | Найдены блокирующие замечания | Ошибка запуска |
| `git-preview` | Git объединил автоматически | Git обнаружил конфликт | Ошибка Git |

Для CI используйте `check`, а не только успешный код подготовки сессии.

Если входящий коммит уже включён в HEAD, `prepare` завершается с кодом 0 и не создаёт сессию. С `--json` этот случай возвращает объект `{"status": "already_integrated", "message": "..."}`. Перед использованием пути кандидата проверяйте статус.
