# Руководство пользователя merge1c

Это основная инструкция. Она объясняет весь рабочий путь: от установки до получения отдельной Git-ветки с результатом. Справочник всех параметров находится в [настройках](configuration.md); для обычного запуска достаточно этой страницы и комментариев в TOML.

## 1. Что делает библиотека

merge1c объединяет исходники файловой выгрузки Конфигуратора. На входе три версии:

- **base** — общее исходное состояние;
- **local** — наша версия с доработками;
- **incoming** — новая поставка или обновлённый master.

Входящая версия служит основой оформления. В неё переносятся наши независимые изменения. Для формы новые элементы поставщика остаются выше наших добавлений в прежнем промежутке. Свободные ID сохраняются; коллизии поддержанных ID согласуются по областям. Для BSL можно совместить независимые изменения разных методов.

Результат появляется в отдельной **сессии**. Исходные рабочие файлы и существующие ветки не заменяются. Если решение неоднозначно, программа оставляет задачу для человека. Не все конфликты можно убрать автоматически без знания смысла доработки.

Для репозитория программа сама берёт текущий коммит HEAD, входящий коммит и единственное общее основание. Незакоммиченные файлы не входят в эти снимки. В `report.json` отдельно учитываются структурные замечания, внешние проверки и проверка 1С.

## 2. Установить программу

Нужен Git 2.50 или новее. Для Windows x64 есть готовая папка `dist/merge1c-0.1.2-windows-x64` и такой же ZIP. Скопируйте или распакуйте **всю** папку в доступное место, например `C:/Tools/merge1c`. Внутри должны остаться `merge1c.exe`, `_internal` и документация. Установка Python для этого способа не требуется.

Добавьте `C:/Tools/merge1c` в пользовательский PATH, откройте новый терминал и выполните `merge1c --version`. В PATH добавляется папка, а не файл exe. До настройки PATH можно вызвать exe напрямую:

```powershell
& 'C:/Tools/merge1c/merge1c.exe' --version
```

В cmd та же команда без `&`: `"C:/Tools/merge1c/merge1c.exe" --version`. Ответ — `merge1c 0.1.2`. Подкаталог `_internal` содержит Python и библиотеки; отдельно перенесённый exe работать не будет. Программа запускается прямо из поставки, без распаковки во временный каталог при каждом старте.

Если вы хотите использовать библиотеку из Python, нужен Python 3.11 или новее. Ниже каталог проекта — `C:/i-merge/merge1c`. При другом расположении укажите свой путь. Команды подходят и для cmd, и для PowerShell:

```text
python --version
git --version
python -m pip install --upgrade "C:/i-merge/merge1c/dist/merge1c-0.1.2-py3-none-any.whl"
python -m merge1c --version
```

Ожидаемый ответ последней команды: `merge1c 0.1.2`. Если wheel отсутствует, установите каталог с исходниками: `python -m pip install "C:/i-merge/merge1c"`. Для сборки из исходников pip может потребоваться интернет.

`No module named merge1c` означает, что выбранный Python не находит установленный пакет. Установка выполняется через `python -m pip`, чтобы использовать тот же интерпретатор. Добавление папки проекта в PATH и копирование её в Scripts не заменяют установку. Если отсутствует сам pip, выполните `python -m ensurepip --upgrade`.

Все дальнейшие примеры используют `python -m merge1c`: этот способ не требует добавлять Scripts в PATH. **В переносимой поставке замените `python -m merge1c` на `merge1c`; остальные аргументы одинаковы.** Короткая команда после установки wheel также доступна, если созданный pip файл `Scripts/merge1c.exe` находится в PATH. Этот запускатель привязан к установленному Python; переносить его отдельно нельзя. Менеджер установки новых Python также может требовать `py install --refresh` после установки пакета; к старому Python Launcher эта команда не относится.

Если готовых файлов нет, порядок сборки wheel и Windows-поставки находится в [разработке](development.md#собрать-поставку). Готовая поставка не требует build или PyInstaller на компьютере пользователя.

## 3. Создать и понять настройки

Для примера исходный репозиторий находится в `C:/REP/erp`:

```text
python -m merge1c init "C:/REP/erp"
```

Создаются два файла:

| Файл | Назначение |
|---|---|
| `merge1c.toml` | Общие правила. Можно хранить в Git |
| `merge1c.local.example.toml` | Образец путей конкретного компьютера |

В новых файлах каждый параметр объяснён непосредственно над его значением. Скопируйте локальный образец в `merge1c.local.toml`, исправьте пути программ и исключите этот файл из Git.

Если настройки уже существуют, `init` их не заменит. Чтобы получить новый комментированный образец рядом со старыми настройками:

```text
python -m merge1c config --write-example "C:/REP/erp/merge1c.example.toml"
```

Образец не подключается автоматически. Сравните его со своими настройками и перенесите нужные значения. Команда работает даже при ошибке в существующем TOML и не заменяет уже созданный файл образца.

В первую очередь проверьте эти параметры:

| Параметр | Что выбрать |
|---|---|
| `project.source_roots` | `[]` — всё дерево. Или относительные пути, например `['src/cf', 'src/cfe']`. Полный путь к репозиторию здесь не нужен |
| `storage.session_root` | Доступный каталог для сессий **вне** исходного репозитория |
| `git.executable` | Имя `git` в PATH или путь к `git.exe` |
| `tools.beyond_compare.executable` | Путь к установленному Beyond Compare |
| `validation.require_platform` | `true` требует реального внешнего адаптера проверки 1С. При `false` возможна только статическая готовность |

Списки и текст в TOML записываются так:

```toml
[project]
source_roots = ['src/cf', 'src/cfe']

[storage]
session_root = 'C:/Temp/merge-sessions'
```

Если раздел уже существует, измените его значение на месте. Повторять `[project]` или `[storage]` в одном файле не нужно. Пути Windows удобно писать через `/` или в одинарных кавычках: `'C:\Temp\merge-sessions'`.

## 4. Выбрать доступное место для сессий

Не всем пользователям разрешено создавать каталоги в корне диска C:. В `merge1c.local.toml` можно задать:

```toml
[storage]
session_root = 'C:/REP/merge-sessions'
```

Другой вариант — `C:/Temp/merge-sessions`, если там есть нужные права. Пустая строка `''` выбирает временный каталог текущего пользователя с подпапкой `merge1c-sessions`. Этот каталог не очищается библиотекой как обычный временный файл; сохраняйте ещё нужные сессии и учитывайте внешнюю очистку TEMP.

Проверить место до объединения:

```text
python -m merge1c doctor --repo "C:/REP/erp" --storage-only
```

Проверка создаёт собственный пробный подкаталог, записывает и читает файл, заменяет его, переименовывает файл и каталог, затем удаляет пробные данные. Существующие файлы и ACL не меняются. Нужны все перечисленные права, а не только право записи.

Если используете `--session`, проверьте именно этот путь:

```text
python -m merge1c doctor --repo "C:/REP/erp" --session "C:/Temp/merge-sessions/erp-update" --storage-only
```

`--session` имеет приоритет над настройкой. Автоматически переходить в другой каталог при отказе доступа программа не будет. Временные снимки Git, проверочные файлы и временный index создаются рядом с выбранной сессией, а не в недоступном системном TEMP.

## 5. Подготовить обновление поставки

Сначала проверьте текущую ветку и состояние репозитория обычным Git. Для вашего процесса это ветка `update/2.5.27.101`, созданная от нужного master. merge1c не переключает её самостоятельно и использует только закоммиченный HEAD.

```text
git -C "C:/REP/erp" status
python -m merge1c prepare vendor/2.5.27.101 --repo "C:/REP/erp"
```

Программа проверит каталог хранения, найдёт общее основание, выгрузит точные байты коммитов, объединит файлы и проверит структуру результата. Каталог сессии с уникальным именем будет создан в `storage.session_root`; его полный путь выводится на экран.

Можно задать имя и полный путь явно:

```text
python -m merge1c prepare vendor/2.5.27.101 --repo "C:/REP/erp" --session "C:/Temp/merge-sessions/erp-update"
```

В этой и следующих командах `C:/Temp/merge-sessions/erp-update` — пример. Заменяйте его на фактический путь своей сессии. Уже существующий каталог не перезаписывается; для нового запуска выбирайте новый путь или опустите `--session`.

Внутри сессии:

| Путь | Что находится внутри |
|---|---|
| `candidate/` | Кандидат для просмотра, ручной правки и проверки |
| `inputs/` | Сохранённые исходные стороны. Их нельзя менять при продолжении сессии |
| `report.json` | Текущая сводка замечаний и решений |
| `session.json` | Состояние и снимок настроек |
| `events.jsonl` | Журнал действий |
| `resolutions/` | История ручных решений и предыдущие версии файлов |

## 6. Посмотреть результат и решить оставшиеся случаи

```text
python -m merge1c status "C:/Temp/merge-sessions/erp-update"
python -m merge1c diff "C:/Temp/merge-sessions/erp-update" "src/cf/CommonForms/Пример/Ext/Form.xml"
```

Три состояния:

| Состояние | Что делать |
|---|---|
| `conflicts` | Разобрать указанные файлы или ошибки структуры |
| `prepared` | Кандидат подготовлен, но обязательные проверки ещё не завершены |
| `ready` | Проверки, требуемые сохранённой политикой, пройдены |

Запуск настроенного Beyond Compare:

```text
python -m merge1c resolve "C:/Temp/merge-sessions/erp-update" "src/cf/CommonForms/Пример/Ext/Form.xml" --tool
```

`--tool` без имени выбирает `resolution.manual_tool`. Программа получает отдельные копии сторон и должна сохранить результат в выделенный файл. Ошибка, отмена или отсутствие результата не принимаются как успешное решение.

Для осознанного выбора всей стороны файла:

```text
python -m merge1c resolve "C:/Temp/merge-sessions/erp-update" "путь/к/файлу.xml" --take local
```

Доступны `base`, `local` и `incoming`. Это выбор **целого файла**, а не только спорного участка. Если на выбранной стороне файл отсутствует, принимается его удаление.

Также можно отредактировать файл непосредственно в `candidate/`, затем подтвердить конкретный случай через `resolve СЕССИЯ ПУТЬ --accept`. Проверки структуры повторятся; подтверждение не скрывает ошибку XML или найденный дубль.

## 7. Проверить кандидат и создать ветку

```text
python -m merge1c check "C:/Temp/merge-sessions/erp-update" --run-tools
python -m merge1c branch "C:/Temp/merge-sessions/erp-update" review/erp-update
```

По умолчанию `require_platform = true`. Для готовности нужен настроенный адаптер, который действительно выполнил проверки 1С и подтвердил ожидаемую версию. Встроенной настроенной информационной базы и универсальной команды загрузки здесь нет. Протокол адаптера описан в [справочнике](configuration.md).

При сознательном `require_platform = false` может быть создан кандидат после структурных и дополнительных обязательных проверок. `platform: not_run` при этом остаётся видимым и не доказывает работоспособности конфигурации.

`branch` создаёт **новую** ветку с merge-коммитом и двумя родителями. Исходная ветка, рабочие файлы и index не переключаются на результат. Изменившийся HEAD, активный merge/rebase/cherry-pick или непроверенный кандидат блокируют создание.

После отдельной проверки результата переносите review-ветку в целевую ветку обычным Git. Например, при неизменившейся update-ветке возможен `git merge --ff-only review/erp-update`. Только после прикладных испытаний выполняйте обычное включение update в master в своём процессе. Автоматической загрузки в рабочую базу нет.

## 8. Обновить существующий develop из master

Находясь на нужном develop, выполните:

```text
python -m merge1c prepare master --repo "C:/REP/erp" --profile develop_sync
```

Затем повторите просмотр, ручные решения, проверки и создание новой review-ветки. История develop не переписывается. Входящей основой в этом случае является master. Неоднозначные изменения всё ещё требуют решения; отсутствие конфликтов во всех возможных доработках не обещается.

## 9. Продолжить после остановки

Если первоначальная подготовка сохранила `session.json`, снова выполните `status` или `check` с её путём. Повторять `prepare` не нужно. Правка первоначального TOML не меняет уже сохранённые правила сессии; для новых правил создайте новую сессию.

Если подготовка прервалась до создания манифеста, автоматического продолжения пока нет. Сохраните нужные файлы и начните новую сессию в новом каталоге. Исходники не менялись.

После сбоя может остаться `session.lock`. Только убедившись, что прежний процесс завершён, выполните `unlock СЕССИЯ --force`, затем `check`. Эта команда не исправляет права доступа.

После завершения работы с Git-сессией можно выполнить `release-pin СЕССИЯ`. Команда освобождает только её служебную ссылку, удерживающую входные коммиты от GC. Она не удаляет сессию или review-ветку. Для ещё нужной сессии сохраняйте закрепление.

## Все команды

Во всех строках ниже перед командой используется `python -m merge1c`. `СЕССИЯ`, `ПУТЬ` и `ВЕТКА` обозначают ваши фактические значения.

| Команда | Назначение |
|---|---|
| `--version`, `--help` | Версия и общая справка |
| `init КАТАЛОГ` | Новые комментированные настройки без перезаписи существующих |
| `config --config ФАЙЛ` | Показать итоговые настройки указанного проекта |
| `config` | Итоговые настройки текущего каталога в JSON |
| `config --write-example ФАЙЛ` | Новый комментированный образец без чтения старых настроек |
| `doctor --repo РЕПОЗИТОРИЙ` | Доступ к хранению, Git и наличие требуемых программ |
| `doctor --repo РЕПОЗИТОРИЙ --storage-only` | Только реальная проверка операций в каталоге хранения |
| `inspect КАТАЛОГ` | Структурная проверка XML/BSL без объединения |
| `prepare ВЕТКА --repo РЕПОЗИТОРИЙ` | Подготовка слияния текущего HEAD с входящей веткой |
| `merge БАЗА НАШЕ ВХОДЯЩЕЕ` | Подготовка из трёх полных каталогов |
| `status СЕССИЯ` | Состояние с повторной структурной проверкой |
| `diff СЕССИЯ ПУТЬ` | Изменения файла относительно incoming |
| `resolve СЕССИЯ ПУТЬ --tool [ИМЯ]` | Решение внешней программой |
| `resolve СЕССИЯ ПУТЬ --take local` | Принятие выбранной стороны целиком |
| `resolve СЕССИЯ ПУТЬ --accept` | Принятие ручной правки кандидата |
| `check СЕССИЯ --run-tools` | Структурные и настроенные внешние проверки |
| `branch СЕССИЯ НОВАЯ_ВЕТКА` | Новая ветка из проверенного Git-кандидата |
| `events СЕССИЯ --tail 30` | Последние события журнала |
| `git-preview ВЕТКА --repo РЕПОЗИТОРИЙ` | Отдельная диагностика штатного merge-tree без rename-эвристики |
| `release-pin СЕССИЯ` | Освобождение собственной служебной ссылки Git |
| `unlock СЕССИЯ --force` | Снятие оставшейся блокировки после проверки завершения процесса |

`--config`, `--local-config` и `--profile` указываются после `config`, `doctor`, `inspect`, `merge`, `prepare` или `git-preview`. Для продолжения сессии правила уже сохранены, новые настройки не подмешиваются. `--session` у `prepare` и `merge` необязателен; если указан, он заменяет автоматический путь.

Для автоматизации `--json` доступен у команд проверки, подготовки и решения. В stdout идёт JSON, прогресс отдельно в stderr. `--quiet` у `prepare` и `merge` отключает только прогресс, сохраняя журнал. `--json-progress` выдаёт события JSONL и несовместим с `--quiet`.

Коды: `prepare`, `merge`, `resolve` — 0 без нерешённых случаев, 1 с замечаниями, 2 при ошибке запуска. Для окончательной проверки используйте `check`: 0 означает готовность, 1 — нерешённые случаи, 2 — ожидающие обязательные проверки или ошибку. Если входящий коммит уже включён в HEAD, `prepare` возвращает 0 без новой сессии; JSON содержит `status: already_integrated`.

## PowerShell и cmd

Обычный вызов `python -m merge1c ...` одинаков. В PowerShell явный путь к exe в кавычках вызывается с `&`; cmd этого не требует. Код внешней команды в PowerShell — `$LASTEXITCODE`, в cmd — `%ERRORLEVEL%`; сохраняйте его сразу после запуска.

JSON stdout использует ASCII-подстановки для кириллицы; парсер восстанавливает текст. Файлы сессии пишутся непосредственно в UTF-8. PowerShell 5.1 при `>` создаёт UTF-16LE и может форматировать stderr как `NativeCommandError`. Поэтому для автоматизации в нём используйте `--quiet --json` и готовые `report.json`/`events.jsonl`, а не ожидайте чистый JSONL от `2>`. Кодировку сохранённого отчёта при чтении задавайте явно: `Get-Content -LiteralPath ПУТЬ -Raw -Encoding UTF8 | ConvertFrom-Json`.

## Что готово и что остаётся

В 0.1.2 реализованы Python API и CLI, трёхсторонние снимки, предметное сопоставление метаданных, ограниченное объединение XML и BSL, согласование поддержанных ID, сессии, журнал, ручные решения, запуск внешних проверок и новая ветка-кандидат. Поддержаны собственный каталог хранения и ранняя проверка доступа. Сохранённые сессии 0.1.1 остаются читаемыми.

Автоматически не решаются все изменения одного метода, сложные перемещения и неизвестные числовые ссылки формы. Роли, СКД, XDTO и обычные формы не имеют отдельных полноценных движков. Несколько общих оснований Git, submodules, символические ссылки и junctions отклоняются. Лексический анализ BSL не является компилятором. Прерванная начальная подготовка ещё не возобновляется.

Проверки на искусственных данных и временных репозиториях не подтверждают загрузку полной ERP или СППР. Перед использованием результата нужны реально настроенная проверка платформой и прикладные испытания. Настоящие 1С и Beyond Compare в среде разработки не запускались.
